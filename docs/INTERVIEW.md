# 有我在面试讲稿

## 30 秒项目介绍

“有我在”是我为 AI 解决方案岗位制作的全栈验证型 MVP。它用陪伴聊天降低情绪记录门槛，把对话整理成用户确认的记录，并通过每周来信形成长期价值。高风险场景不依赖模型自由发挥，而是进入确定性安全流程；守护通知受逐项授权和再次确认控制。

## 我具体做了什么

- 从用户问题出发定义 MVP 范围和非目标。
- 设计聊天、记录、来信、守护圈和 High Risk 的完整流程。
- 实现 Next.js 前端、服务端 API、SQLite、认证与权限。
- 抽象 LLM 和 TTS Provider，并设计离线或浏览器降级。
- 为风险、权限、展示和语音并发建立 35 项自动化测试。
- 把需求、规格、架构、测试和决策沉淀为 SDD 资料。

## 最难的问题

### 安全不能只靠提示词

我的处理是把 High Risk 作为确定性业务工作流。模型可以参与普通陪伴和结构化抽取，但不能把规则判定的 high 降级。通知还要经过事先授权和用户确认。

### 浏览器自动播放不是设置一个布尔值

真正的问题包括用户手势、AudioContext 状态、异步 TTS、旧请求竞争和页面生命周期。我最终使用全局播放管理器，把解锁、请求取消、暂停恢复、切页停止和 speaking 状态放在同一状态源中。

### 外部 AI 不稳定

LLM 和 TTS 都可能因网络、额度、超时或格式错误失败。因此核心文字路径采用 Provider + fallback，且界面诚实展示降级状态。

## 如何证明不是只有前端

现场展示登录 Session、SQLite 表、API Route、保存后跨页面读取、守护权限裁剪、通知状态和自动化测试。项目采用单仓库全栈架构，前后端逻辑分层，但不是两个独立部署仓库。

## 如何说明 Vibe Coding 能力

“我不是只让 AI 生成页面，而是先固定 PRD、Spec、风险边界和验收标准，再让 AI 在限定范围内实现。每次迭代都要经过测试、构建和浏览器验证，重大取舍写入 ADR，失败和外部限制如实进入版本记录。”

## 必须诚实说明的限制

- 还没有真实用户留存和商业转化数据。
- 当前守护通知是站内模拟。
- SQLite 和本地 Session 尚不是生产级多实例方案。
- 自然 TTS 依赖有效 Provider 额度。
- 安全文案还需要专业人员和地区资源审阅。

## 面试官可能追问

**为什么不用纯 LLM 做风险判断？** 因为概率输出不适合作为唯一安全控制，确定性规则能提供最低保障。

**为什么不自动通知守护人？** 因为敏感信息分享需要明确授权和当次控制权，减少误报造成的二次伤害。

**为什么先用 SQLite？** 它足以证明真实数据闭环并降低 Demo 环境成本；真实试点再根据并发和部署模式迁移。

**接下来最重要的工作是什么？** 不是继续加功能，而是部署 Beta、完成真实用户测试、补 CI 和生产安全能力。
