# 有我在规范驱动开发流程

## 目的

用可追踪的规范约束 AI 编码，避免只凭对话临时修改。每个版本都从问题和验收标准开始，以测试、构建和人工验证结束。

## 标准流程

1. **问题定义**：写清用户、场景、痛点和不解决的范围。
2. **PRD**：确定用户流程、产品原则和成功指标。
3. **Spec**：给需求编号，定义状态、接口、失败行为和验收标准。
4. **界面验证**：先验证关键流程和信息结构，再完善服务端实现。
5. **技术设计**：记录模块边界、数据模型、Provider 和安全约束。
6. **任务拆分**：每项任务绑定需求编号、目标文件和测试。
7. **实现**：小批次修改，禁止顺手扩大范围。
8. **验证**：依次执行测试、构建和标准 Demo；保存真实结果。
9. **决策记录**：重大取舍写入 `DECISIONS.md`。
10. **版本交付**：更新 `CHANGELOG.md`、已知问题和作品集材料。

## 需求追踪模板

```text
需求编号：VOICE-03
用户问题：连续回复会造成声音重叠
预期行为：任何时刻最多播放一条语音
非目标：复杂唇形同步
影响模块：voice-playback、voice-player、layout
自动化测试：rapid replacement / stale response / page cleanup
人工验收：播放中触发第二条、切页
结果：通过 / 失败及证据
```

## 完成定义

- 需求和非目标清楚。
- 代码与现有架构一致。
- 对应自动化测试通过。
- `pnpm build` 通过。
- 关键路径在浏览器中验证。
- 外部依赖失败时行为明确。
- 文档和已知问题同步更新。
- 没有密钥、用户隐私或测试账号的真实敏感数据进入提交。

## 变更控制

如果实现过程中发现新问题，先判断是否阻断当前验收。阻断项进入当前版本；非阻断项进入路线图。不得因为 AI 建议了“更完整的方案”就自动扩大产品范围。

## 证据保存

每个版本保留需求编号、提交记录、测试输出、构建输出、演示截图和已知问题。当前目录尚未初始化 Git，因此提交历史属于待补齐证据，不能在面试中声称已有完整版本轨迹。
